# M2 prior art

Research date: 2026-11-05. Scope: offline core/query contracts, fixture data and
retrieval baseline. S4's SQLite build and trigger findings are in [S4.md](S4.md).

- [SQLite FTS5 reference](https://www.sqlite.org/fts5.html): quote literal terms and
  double embedded quotes before binding MATCH expressions. SQLite returns lower
  BM25 scores for better matches. The parser/compiler must preserve this orientation;
  SQL parameter binding alone does not neutralize FTS operators.
- [sqlitesearch issue 24](https://github.com/alexeygrigorev/sqlitesearch/issues/24):
  a raw fallback for punctuation-only input can raise FTS syntax errors. Test empty,
  punctuation, quotes and operator-looking input through the actual compiler path.
- [sqlite-data discussion 329](https://github.com/pointfreeco/sqlite-data/discussions/329):
  clearing a search input exposed malformed FTS expressions. Define empty-input
  behavior explicitly rather than constructing an empty MATCH clause.

GitHub and official documentation were searched, together with Reddit and X.
Reddit search results raised the same quote/operator-injection and hyphen issues;
they are leads corroborated by SQLite's grammar, not independent design authority.
X search produced no useful primary implementation evidence. No social claim is
used as a requirement.

Implementation direction: retain a typed AST, compile quoted literal FTS terms,
keep timezone conversion outside the I/O-free core, and use a documented deterministic
ranking baseline until the M2 eval runner measures it. Fictional fixture identifiers and references
must be validated before retrieval evaluation; generated volume alone is not evidence
of useful answers. Citation framing is a representation boundary, not a claim that
language models cannot follow malicious text.

## Retrieval baseline (measured 2026-11-05)

`teamctx eval` (definitions in `crates/teamctx/src/eval.rs`) runs the 62 questions of
`fixtures/demo/eval.toml` against the demo dataset, 314 messages and 76 entries. Both
tools return a message list and an entry list, each cut at 10, scored against that
collection's gold only. The stored baseline is `fixtures/demo/eval-baseline.toml`.

| Tool | Collection | recall@10 | MRR |
|---|---|---|---|
| `search` | messages | 0.0000 | 0.0000 |
| `search` | entries | 0.0000 | 0.0000 |
| `context_for` | messages | 0.0000 | 0.0000 |
| `context_for` | entries | 0.0000 | 0.0000 |

Every category (date, name, paraphrase, reversed, thread-context) is 0.0000 as well.
This is the honest number, not a wiring fault: a unit test shows the same pipeline
finds the gold for `Fenwick Serif`. The cause is the contract. The query clauses combine
with AND, so a full question such as "Which typeface do we use for the main reading
text?" needs every word, stopwords included, in one message or entry title. `context_for`
drops stopwords but still ANDs the remaining words. Nothing in the dataset contains them
all. Neither the query, the ranking nor the dataset was tuned to change this.

### Suggestions (not built; each needs the plan's acceptance rule in section 9.1)

A throwaway experiment (not committed) ran the `context_query` words one at a time with
OR semantics and ranked items by how many of the words they matched, ties by summed
`bm25`. Same cases, same cutoff, per-collection gold:

| Category | cases | messages recall@10 | messages MRR | entries recall@10 | entries MRR |
|---|---|---|---|---|---|
| date | 9 | 0.8889 | 0.5019 | 1.0000 | 0.9444 |
| name | 9 | 0.8889 | 0.6704 | 1.0000 | 1.0000 |
| paraphrase | 22 | 0.0455 | 0.0091 | 0.5000 | 0.1926 |
| reversed | 13 | 0.6154 | 0.2842 | 1.0000 | 0.7564 |
| thread-context | 9 | 0.2593 | 0.3704 | 0.7778 | 0.4037 |
| overall | 62 | 0.4409 | 0.2867 | 0.7903 | 0.5678 |

1. **Match any query word and rank by how many match** (OR with a bm25 tie-break), for
   `context_for` at least. This alone moves entries from 0 to 0.79 recall@10, the
   largest single improvement available without new dependencies. Keep AND for quoted
   phrases and filters in `search`.
2. **Paraphrase stays low on messages** (0.0455) by design: those questions share no
   content word with their answer. Only expansion (synonyms, embeddings with
   `sqlite-vec`, or an agent issuing several searches) can help; measure before adding.
3. **Thread-context** needs the neighbouring messages of plan section 9, step 3. The
   eval does not add them yet; scoring `context_for` over the expanded bundle would show
   their value. That is a metric change and should be made before the ranking work.
4. **Entry search covers title and tags only**, so message-side recall will trail
   entry-side recall whenever a question names a detail that lives in message text.
5. With an all-zero baseline the CI gate cannot yet catch a regression. The first
   retrieval change that raises a number should rewrite the baseline in the same commit
   (`cargo xtask eval -- --write-baseline`). Done: see "Retrieval v2" below.

## Retrieval v2: bare words match any term (measured 2026-11-05)

Change: bare words are OR alternatives ranked by SQLite `bm25` (more matched terms score
higher); quoted phrases and the `from:`/`in:`/`before:`/`after:` filters stay required.
Stopwords (a fixed list in `core::query`, shared with `context_for`) and repeated words
are dropped from the bare words; a query of only stopwords keeps them so it still
searches. Terms are still quoted literals bound as one parameter. The `topic` filter of
`list_entries` keeps AND (`fts_expression_all`). `core::rank` is unchanged: the eval does
not apply it, so these numbers cannot justify a change there.

Acceptance rule (plan section 9.1): overall recall@10 or MRR up by at least 3 points,
neither down by more than 1 point, for `search` and `context_for`. Combined (message and
entry mean) overall numbers, before and after:

| Tool | recall@10 before | after | MRR before | after |
|---|---|---|---|---|
| `search` | 0.0000 | 0.6102 | 0.0000 | 0.4286 |
| `context_for` | 0.0000 | 0.6142 | 0.0000 | 0.4326 |

Both tools pass. Per collection, overall:

| Tool | messages R@10 | messages MRR | entries R@10 | entries MRR |
|---|---|---|---|---|
| `search` before | 0.0000 | 0.0000 | 0.0000 | 0.0000 |
| `search` after | 0.4301 | 0.2831 | 0.7903 | 0.5741 |
| `context_for` before | 0.0000 | 0.0000 | 0.0000 | 0.0000 |
| `context_for` after | 0.4382 | 0.2911 | 0.7903 | 0.5741 |

Per category, combined recall@10 / MRR (every "before" value is 0.0000 / 0.0000):

| Category | cases | `search` after | `context_for` after |
|---|---|---|---|
| date | 9 | 0.8889 / 0.7241 | 0.8889 / 0.7241 |
| name | 9 | 0.9444 / 0.8148 | 0.9444 / 0.8148 |
| paraphrase | 22 | 0.3068 / 0.1363 | 0.3068 / 0.1363 |
| reversed | 13 | 0.7500 / 0.4638 | 0.7692 / 0.4831 |
| thread-context | 9 | 0.5370 / 0.4105 | 0.5370 / 0.4105 |

The two tools differ only in the reversed category. Messages are scored against message
gold only, so the message and entry rows above are not comparable with each other.

What was tried, one change at a time (`search`, combined overall recall@10 / MRR):

| Step | recall@10 | MRR | Kept |
|---|---|---|---|
| 1. OR over all bare words, no stopword removal | 0.6035 | 0.4230 | no |
| 2. OR plus stopword removal (the shipped rule) | 0.6102 | 0.4286 | yes |
| 3. Step 2 plus column weights `bm25(record_fts, 5.0, 1.0)` (title over tags) | 0.6183 | 0.4268 | no |

Step 1 alone already clears the rule: `bm25`'s inverse document frequency downweights
common words, so removing stopwords adds only about 0.7 points of recall@10 and 0.6 of
MRR. It stays because the plan asks for it and `context_for` already did it. Step 3
moved recall@10 up 0.8 points and MRR down 0.2 points, which is noise on 62 cases, so it
was reverted. The earlier throwaway experiment (rank by count of matched words, then
summed `bm25`) measured 0.4409 message recall@10, close to the 0.4301 and 0.4382 shipped
here, so plain `bm25` is enough.

### Remaining gap and options (not built, no dependency added)

- **Paraphrase** is the weak spot (combined 0.31 recall@10; messages 0.11). Those
  questions share no content word with their answer, so no lexical matcher finds them.
  Options: embeddings with `sqlite-vec` (a dependency decision under ADR 0011), a small
  synonym table for the team's vocabulary, or an agent issuing several searches. Measure
  each with this eval before adding it.
- **Stemming** is already on: both FTS tables use the `porter unicode61` tokenizer. A
  heavier stemmer or lemmatiser would be a new dependency; measure before adding one.
- **Thread-context** (messages 0.30 recall@10) needs the neighbouring messages of plan
  section 9, step 3, and a metric that scores the expanded bundle.
- **Entry search covers title and tags only**, so message-side recall trails entry-side
  recall for questions about details that live in message text.

## The eval measures the production path (measured 2026-11-05)

Problem: the first runner called the store's `search_entries` and `search_messages`
directly, so `core::rank` (recency decay, entry boost), the `/ask` merge of the all-terms
and single-term queries in `Bundle::retrieve`, and neighbour expansion were never
measured. A ranking regression could not fail CI.

Change: `search` and `context_for` now call `rank_candidates`, the merge `teamctx search`
runs (entries and messages scored with `core::rank::score`, sorted together, then split by
kind and cut at 10). A third tool, `ask_retrieval`, calls `teamctx_llm::Bundle::retrieve`
with the default limits. The clock is fixed so recency is reproducible. `ask_retrieval`
counts the whole bundle (at most 24 items): recall is any gold id in the bundle, and MRR
uses prompt position, which for messages is conversation and time order, so message MRR
there is a weak signal (0.09). Compare `ask_retrieval` recall with the others, not its
message MRR. A test runs the eval with a reversed scorer and shows `--check` fails.

Combined overall numbers, before (raw store order) and after (production path):

| Tool | recall@10 before | after | MRR before | after |
|---|---|---|---|---|
| `search` | 0.6102 | 0.5941 | 0.4286 | 0.4005 |
| `context_for` | 0.6142 | 0.6022 | 0.4326 | 0.4046 |
| `ask_retrieval` | n/a | 0.6465 | n/a | 0.3132 |

Per collection, overall, after:

| Tool | messages R@10 | messages MRR | entries R@10 | entries MRR |
|---|---|---|---|---|
| `search` | 0.3978 | 0.2653 | 0.7903 | 0.5358 |
| `context_for` | 0.4140 | 0.2760 | 0.7903 | 0.5331 |
| `ask_retrieval` | 0.5027 | 0.0892 | 0.7903 | 0.5371 |

Findings:

- The production ranking is slightly worse than raw bm25 on this set (search messages
  recall 0.4301 to 0.3978, MRR 0.2831 to 0.2653). Recency decay favours newer messages
  over older, better-matching ones. The set has few time-sensitive questions, so this is
  a tuning lead (decay half-life, boost), not a conclusion; any change must meet the
  section 9.1 rule against this baseline.
- The `/ask` bundle finds more message gold than either 10-result list (0.5027 against
  0.3978 and 0.4140), mostly in thread-context (0.5741 against 0.2963 and
  0.3519). That is the neighbour expansion and the single-term queries doing their job, now measured.
- Entry recall is unchanged at 0.7903 for all three tools: entry order does not move the
  top 10 here.
- The baseline moved down for `search` and `context_for` because the measurement got
  more honest, not because retrieval got worse for users. The old numbers described a
  path users never ran.
