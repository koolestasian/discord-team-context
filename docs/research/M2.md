# M2 prior art

Research date: 2026-11-05. Scope: offline core/query contracts, fixture data and
retrieval baseline. S4's SQLite build and trigger findings are in [S4.md](S4.md).

- [SQLite FTS5 reference](https://www.sqlite.org/fts5.html): quote literal terms and
  double embedded quotes before binding MATCH expressions. SQLite returns lower
  BM25 scores for better matches. The parser/compiler must preserve this orientation;
  SQL parameter binding alone does not neutralize FTS operators.
- [sqlitesearch issue 24](https://github.com/alexeygrigorev/sqlitesearch/issues/24):
  a raw fallback for punctuation-only input can raise FTS syntax errors. Test empty,
  punctuation, quotes and operator-looking input through the actual compiler path.
- [sqlite-data discussion 329](https://github.com/pointfreeco/sqlite-data/discussions/329):
  clearing a search input exposed malformed FTS expressions. Define empty-input
  behavior explicitly rather than constructing an empty MATCH clause.

GitHub and official documentation were searched, together with Reddit and X.
Reddit search results raised the same quote/operator-injection and hyphen issues;
they are leads corroborated by SQLite's grammar, not independent design authority.
X search produced no useful primary implementation evidence. No social claim is
used as a requirement.

Implementation direction: retain a typed AST, compile quoted literal FTS terms,
keep timezone conversion outside the I/O-free core, and use a documented deterministic
ranking baseline until the M2 eval runner measures it. Fictional fixture identifiers and references
must be validated before retrieval evaluation; generated volume alone is not evidence
of useful answers. Citation framing is a representation boundary, not a claim that
language models cannot follow malicious text.

## Retrieval baseline (measured 2026-11-05)

`teamctx eval` (definitions in `crates/teamctx/src/eval.rs`) runs the 62 questions of
`fixtures/demo/eval.toml` against the demo dataset, 314 messages and 76 entries. Both
tools return a message list and an entry list, each cut at 10, scored against that
collection's gold only. The stored baseline is `fixtures/demo/eval-baseline.toml`.

| Tool | Collection | recall@10 | MRR |
|---|---|---|---|
| `search` | messages | 0.0000 | 0.0000 |
| `search` | entries | 0.0000 | 0.0000 |
| `context_for` | messages | 0.0000 | 0.0000 |
| `context_for` | entries | 0.0000 | 0.0000 |

Every category (date, name, paraphrase, reversed, thread-context) is 0.0000 as well.
This is the honest number, not a wiring fault: a unit test shows the same pipeline
finds the gold for `Fenwick Serif`. The cause is the contract. The query clauses combine
with AND, so a full question such as "Which typeface do we use for the main reading
text?" needs every word, stopwords included, in one message or entry title. `context_for`
drops stopwords but still ANDs the remaining words. Nothing in the dataset contains them
all. Neither the query, the ranking nor the dataset was tuned to change this.

### Suggestions (not built; each needs the plan's acceptance rule in section 9.1)

A throwaway experiment (not committed) ran the `context_query` words one at a time with
OR semantics and ranked items by how many of the words they matched, ties by summed
`bm25`. Same cases, same cutoff, per-collection gold:

| Category | cases | messages recall@10 | messages MRR | entries recall@10 | entries MRR |
|---|---|---|---|---|---|
| date | 9 | 0.8889 | 0.5019 | 1.0000 | 0.9444 |
| name | 9 | 0.8889 | 0.6704 | 1.0000 | 1.0000 |
| paraphrase | 22 | 0.0455 | 0.0091 | 0.5000 | 0.1926 |
| reversed | 13 | 0.6154 | 0.2842 | 1.0000 | 0.7564 |
| thread-context | 9 | 0.2593 | 0.3704 | 0.7778 | 0.4037 |
| overall | 62 | 0.4409 | 0.2867 | 0.7903 | 0.5678 |

1. **Match any query word and rank by how many match** (OR with a bm25 tie-break), for
   `context_for` at least. This alone moves entries from 0 to 0.79 recall@10, the
   largest single improvement available without new dependencies. Keep AND for quoted
   phrases and filters in `search`.
2. **Paraphrase stays low on messages** (0.0455) by design: those questions share no
   content word with their answer. Only expansion (synonyms, embeddings with
   `sqlite-vec`, or an agent issuing several searches) can help; measure before adding.
3. **Thread-context** needs the neighbouring messages of plan section 9, step 3. The
   eval does not add them yet; scoring `context_for` over the expanded bundle would show
   their value. That is a metric change and should be made before the ranking work.
4. **Entry search covers title and tags only**, so message-side recall will trail
   entry-side recall whenever a question names a detail that lives in message text.
5. With an all-zero baseline the CI gate cannot yet catch a regression. The first
   retrieval change that raises a number should rewrite the baseline in the same commit
   (`cargo xtask eval -- --write-baseline`).
