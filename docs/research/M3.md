# M3 offline connector prior art

Research date: 2026-11-05. Scope: permissions, bot invite, configuration and offline
init/doctor. Live ingestion, token validation and interaction replies remain gated on
S1/S2 in a throwaway server.

- [Discord permission hierarchy](https://docs.discord.com/developers/topics/permissions):
  compute everyone base plus role union, everyone overwrite, aggregated role deny/allow,
  then member deny/allow. Administrator and guild ownership bypass overwrites. Role
  ordering must not affect the result. View denial makes history unreadable even if the
  history bit remains set. Tests cover these boundaries and extra permissions warnings.
- [Discord bot authorization](https://docs.discord.com/developers/topics/oauth2#bot-authorization-flow):
  the bot scope authorizes guild installation; application commands are included by
  default, but are explicit in our invite. The local builder fixes permissions to
  1024 | 65536 = 66560 and accepts numeric IDs so query parameters cannot be injected.
- [Discord gateway privileged intents](https://docs.discord.com/developers/events/gateway#privileged-intents):
  requesting an intent and enabling it in the portal are separate requirements. The
  setup guide asks for Message Content, without Presence or Server Members.
- [Official API docs issue 4775](https://github.com/discord/discord-api-docs/issues/4775)
  (GitHub search lead: message content missing despite intent settings) prompted an
  explicit separation of offline token presence from live content-access verification.
  No behavior is inferred from the issue; the gateway documentation is authoritative.
- [Official message resource](https://github.com/discord/discord-api-docs/blob/main/developers/resources/message.mdx)
  documents empty history results without Read Message History. Seeing live events is
  therefore insufficient evidence of backfill permissions.
- [toml deserialization API](https://docs.rs/toml/latest/toml/fn.from_str.html): use serde
  typed configuration with unknown-field rejection, not a bespoke TOML parser. `serde`
  derives and `toml` are approved plan section 17 dependencies, introduced when first
  used. Standard library alone was considered; it does not parse the plan's TOML format.

Reddit and X were searched. Reddit search-result leads about denied history still
being visible highlighted role overwrite interactions; those observations were checked
against Discord's algorithm rather than treated as requirements. X returned no useful
primary implementation evidence. No social claim is used as a factual specification.

## Live connector: gateway reconnect and resume (2026-11-09)

Scope: `teamctx run` (gateway loop, catch-up after reconnect, REST client) and
`doctor --live`. Sources were read on 2026-11-09; none of this was tried against a
live Discord server, because no test bot credentials were available.

- [twilight book, gateway chapter](https://github.com/twilight-rs/twilight/blob/f3bf23257ffb799c28c7a885a2dc4acc2e449e83/book/src/chapter_1_crates/section_3_gateway.md)
  and the [twilight-gateway README](https://github.com/twilight-rs/twilight/blob/f3bf23257ffb799c28c7a885a2dc4acc2e449e83/twilight-gateway/README.md):
  a `Shard` reconnects, resumes and identifies by itself and can hand out raw
  websocket messages. We read raw text frames and keep `crate::mapping` the only
  payload interpreter, instead of twilight's typed `Event`, which cannot represent a
  partial `MESSAGE_UPDATE`.
- [twilight 0.15 update notes, 2023-09-10](https://github.com/twilight-rs/twilight/blob/f3bf23257ffb799c28c7a885a2dc4acc2e449e83/book/src/versions/0.15/2023-09-10.md):
  earlier gateway versions swallowed messages on an I/O error and sent commands before
  the resume. Both were fixed in the shard; we send no commands at all, and the
  read-only guard now fails if gateway code calls `send`, `command` or `sender`.
- [discord-api-docs #1619, odd RESUME behaviour](https://github.com/discord/discord-api-docs/issues/1619):
  a failed resume looks like a 1006 network blip, and the session is then replaced by a
  new IDENTIFY, which drops every event in between. So a resume is not proof that
  nothing was missed: teamctx runs discovery and catch-up after `RESUMED` and after
  every `GUILD_CREATE` (which follows a fresh `READY`), as plan section 7.2 says ("after
  every gateway reconnect"). Catch-up is idempotent, so the redundant run after a clean
  resume costs only REST calls.
- [discord-api-docs #5282, `resume_gateway_url`](https://github.com/discord/discord-api-docs/issues/5282):
  resumes must use the URL from READY. twilight 0.18 stores it (`Shard::resume_url`);
  we do not reimplement any of this.
- Discord close codes 4004 (authentication failed) and 4010 to 4014 (shard, version,
  invalid or disallowed intents) are fatal: twilight stops the shard. 4014 is what a
  missing Message Content intent produces, so `run` reports it in words and
  `doctor --live` checks the application flags (`1 << 18`, `1 << 19`) beforehand.
- Pitfalls found in the 0.18 sources themselves (not from issues):
  - `ReceiveMessageError`'s `Display` prints the whole undecodable event, and
    `twilight_http::Error`'s `Display` prints the response body. Both can contain chat
    text, so neither is formatted or logged; only fixed text and status codes are.
  - The shard only heartbeats while it is polled. The gateway loop therefore never
    blocks on storage: dispatches go to an ingest thread through a bounded queue, and
    sync runs on its own thread.
  - `Shard::new` and the HTTP client builder unwrap their TLS setup, and rustls needs
    exactly one crypto provider. The binary gets `aws-lc-rs` through reqwest; the
    constructors are wrapped so a panic becomes a startup error.

What we do differently from the earlier private prototype and typical bots: one guild
only (events for any other guild are dropped before mapping), no gateway commands,
no write endpoints in the REST client (the `Read` enum is the complete list of extra
`GET`s), and catch-up after every reconnect instead of trusting resume.

Reddit and X were not searched again for this step; the GitHub sources above are
primary (library source, maintainers' notes and Discord staff answers).

The offline doctor must not imply successful Discord authentication or effective access
without fetching guild/member/channel data. It reports deferred URL/timezone validation,
Windows ACL checks and private-thread membership explicitly. It never echoes a parsed
value or parser source excerpt on an error, because a pasted token could occupy that
field. Tokens remain in process environment variables; secrets.env loading is deferred.
