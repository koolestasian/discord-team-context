# S4 spike: bundled SQLite FTS5 on every target

Date: 2026-11-05. Question (plan section 18, M1): does `rusqlite` with the bundled SQLite
build and give working FTS5 search on every OS and target we ship, so ADR 0003 can stand?
Social posts and search excerpts are leads; claims below rest on primary sources (crate
source, sqlite.org, NVD) unless marked otherwise. Reddit cannot be scraped here, so Reddit
threads appear only as search excerpts.

## 1. Prior art

**Does `bundled` include FTS5?** Yes. I read `libsqlite3-sys` 0.39.1's `build.rs` (the crate
that `rusqlite` 0.41.1 pulls in with `bundled`): it compiles the vendored amalgamation
(SQLite 3.54.1, source id dated 2026-10-16) with `-DSQLITE_ENABLE_FTS3`, `_FTS5`, `_JSON1`,
`_RTREE`, `_STAT4`, `_COLUMN_METADATA`, `_DBSTAT_VTAB`, `-DSQLITE_THREADSAFE=1` and
`-DSQLITE_DEFAULT_FOREIGN_KEYS=1`. No Cargo feature is needed for FTS5 in bundled mode.
Reports of `no such module: fts5` come from the opposite case: a system SQLite built without
FTS5 (for example [gsd-build/gsd-2#4497](https://github.com/gsd-build/gsd-2/issues/4497),
seen as a search excerpt on 2026-11-05). Bundling is the fix for that class of bug, which is
the reason ADR 0003 chose it.

**musl.** The classic rusqlite/musl failure is a segfault when the build does not use the
bundled copy and ends up with a mismatched dynamic SQLite
([rusqlite#914](https://github.com/rusqlite/rusqlite/issues/914), opened 2021-03-08, still
open and labelled cross-compilation; workaround: enable `bundled`). We always bundle, so
that path is closed. Practical musl needs: a C compiler for the target (`musl-gcc` from
`musl-tools` on Ubuntu) and the `cc` crate finding it. The CI job sets
`CC_x86_64_unknown_linux_musl=musl-gcc` explicitly instead of relying on `cc`'s default
lookup for the target (a precaution; I did not verify what the default would pick). A separate, well-documented musl issue is its default allocator, which is much slower
under multi-threaded allocation
([Tweag, 2023-08-10](https://tweag.io/blog/2023-08-10-rust-static-link-with-mimalloc/),
[nickb.dev](https://nickb.dev/blog/default-musl-allocator-considered-harmful-to-performance/);
a Reddit thread with the same title appeared in search excerpts only). That concerns the
whole binary, not SQLite correctness. It is not in scope for S4; I list it as a follow-up for
the release milestone.

**Windows MSVC.** `build.rs` honours `-C target-feature=+crt-static` (it calls
`cfg.static_crt(true)` when the target feature list contains `crt-static` and the compiler is
MSVC), so the C code is built with `/MT` to match Rust. That matters here: the repository's
`.cargo/config.toml` sets `+crt-static` for MSVC. A mixed `/MT` and `/MD` link would show up as
LNK4098 or duplicate-symbol errors; it did not occur (section 3).

**Build-time knobs worth knowing.** `LIBSQLITE3_FLAGS` (read by `build.rs`, which re-runs when
it changes) lets a project add `-D` flags such as `SQLITE_DEFAULT_MEMSTATUS=0`; atuin uses it
(see `docs/research/M0.md`). Not adopted in S4: no measured need.

**Security floor.** SQLite before 3.50.2 has CVE-2025-6965, a memory corruption bug where the
number of aggregate terms can exceed the number of columns (CVSS 3.1 base 9.8 per the Red Hat
and Wiz entries; NVD lists affected versions as below 3.50.2:
[NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-6965), checked 2026-11-05). The bundled copy
is well above it. The test asserts a floor of 3.50.2 so a future dependency or pin change
cannot silently go back to an unpatched SQLite.

**FTS5 external-content pattern.** The sqlite.org FTS5 page documents exactly the trigger
shape used here (insert, and for update/delete the special `'delete'` command with the old
values) and the `'integrity-check'` command, which compares the index with the content table
when `rank` is 1 ([fts5.html](https://sqlite.org/fts5.html), sections 4.4 and 6.7). The same
page warns that an external-content index silently drifts if the triggers are wrong; the
integrity check in the test is how we catch that.

## 2. What the spike tests

`crates/teamctx-store/tests/fts5.rs`, run against an in-memory database and a temp-file
database (with `journal_mode=WAL`, as ADR 0003 requires):

- compiled SQLite reports `ENABLE_FTS5` and `THREADSAFE=1`, an `fts5` virtual table can be
  created, and the linked library version equals what Rust reports;
- version is at least 3.50.2 (see above);
- an external-content `messages_fts` table with insert, update and delete triggers over a
  small fictional `messages` table, using `porter unicode61 remove_diacritics 2`;
- `MATCH` finds the right rows; `bm25()` ranks a short focused message before a long one
  that mentions the term once; porter stemming (`deploying` finds `deploy`) and diacritics
  (`café` finds `cafe`) work;
- a hostile query bound as a single quoted phrase is treated as text (the escaping rule from
  plan section 13);
- after an update the old term no longer matches and the new one does; after a delete the row
  is gone from search in the same statement; `integrity-check` with `rank=1` passes after each
  step;
- the file database is searchable after being closed and reopened.

I checked that the tests can fail: replacing the `'delete'` command in the triggers with a
no-op made both database tests fail.

## 3. Result

Verified on a Windows x86_64 host (MSVC, static CRT through `.cargo/config.toml`), rustc 1.99.1:

- `cargo test --workspace` passes, including the 3 new tests.
- Bundled SQLite version: **3.54.1** (`libsqlite3-sys` 0.39.1, `rusqlite` 0.41.1).
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo fmt --check`,
  `cargo deny check` and `cargo +1.89 check --workspace --all-targets --locked` pass.
  `rusqlite` 0.41.1 declares `rust-version` 1.89, equal to our MSRV.

Not verified locally, left to CI (the workflow is written, it has
not run):

- Linux (glibc) and macOS: the existing `test (ubuntu-24.04)` and `test (macos-26)` jobs now
  run these tests.
- `x86_64-unknown-linux-musl`: the new `musl` job builds the workspace and runs the tests
  (static musl binaries run on the glibc runner). `aarch64-unknown-linux-musl` is in
  `deny.toml`'s target list but has no CI job; it needs a cross toolchain and is left to the
  release milestone.
- The new job was not run through `zizmor` here (not installed on this host); it copies the
  existing jobs' pinned-SHA, `persist-credentials: false`, top-level `permissions: {}` and
  per-job `contents: read` pattern, and uses no `${{ }}` expressions in `run:` steps.

**Verdict: keep ADR 0003.** Nothing found contradicts it. The one open risk (musl and macOS
actually passing) is checked by CI, and the ADR's rule still applies: if FTS5 fails on any
target, revisit before M2.

## 4. Code disposition

The test file and the two dependency lines (`rusqlite` with `bundled` and default features
off, dev-only `tempfile`) are kept: the test doubles as a platform smoke test. The DDL in it is
**throwaway**; M2 writes the real migrations and their tests (plan section 14). Default
features are off because they only add the statement cache (`hashlink`) and a wasm backend;
M2 can turn on `cache` if it uses `prepare_cached`.
