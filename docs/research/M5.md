# M5 record write path: prior art

Research date: 2026-11-09. Scope: the OKF 0.2 export (plan section 10.5, ADR 0013), the
`md` layout, and how the export treats untrusted chat text. This note covers the
Discord-independent part of M5 (the write rules, store methods, date parser and export);
the slash commands and context menus are built separately.

## OKF 0.2

Source read: [OKF SPEC.md](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md),
the file on `main`, read on 2026-11-09 through a page-summarising fetch tool, twice, with
the second pass asking for verbatim examples. The page says "OKF Version 0.2" and gives no
publication date or revision id, so the date above is when it was read, not when it was
published. Treat the quoted details as read through a summariser: re-check them against the
page before a release.

What the spec says that the export relies on:

- A bundle is a directory tree of UTF-8 Markdown files. `index.md` and `log.md` are
  reserved names; both are optional. A bundle-root `index.md` may declare
  `okf_version: "0.2"` (section 12).
- Every other `.md` file needs YAML frontmatter with a non-empty `type` (section 11).
  `title`, `description`, `resource` and `tags` are recommended. Unknown keys and unknown
  `type` values must be tolerated (section 11), which is what lets us add `id`, `owner`,
  `created`, `updated`, `due`, `supersedes`, `superseded_by` and `entry_status`.
- `sources` is a list of entries with a required `resource` and optional `id`, `title`,
  `author` (section 5.1). Claims cite them as Markdown footnotes; the footnote label must
  equal `sources[].id`. We use `m-<message row id>` as the label.
- `generated: { by, at }` and `verified: { by, at }`; actors are `human:<id>`,
  `process:<id>` or `<producer>/<version>` (sections 5.2, 5.3, 7). "`verified` by a
  `human:<id>` actor means human-reviewed."
- `status` is one of `draft`, `stable`, `deprecated`; absent means `stable` (section 5.4).
- Links are bundle-relative with a leading `/` (section 6.1). `index.md` has no frontmatter
  except `okf_version` and groups `* [Title](url) - description` lines under `#` headings
  (section 8). `log.md` is a newest-first list grouped by `## YYYY-MM-DD` headings with
  bullets that start with a bold word such as `**Update**` or `**Creation**` (section 9).
- Timestamps are ISO 8601 with an explicit UTC offset (we write `...Z`).

Where the plan and the spec differ, and what the export does:

| Plan section 10.5 says | The spec says | Export |
|---|---|---|
| frontmatter `status` | `status` is `draft`/`stable`/`deprecated` only | `status` carries the OKF value (open is `draft`, active, done and answered are `stable`, superseded and dropped are `deprecated`); the exact lifecycle status is in `entry_status`. A plain `status: done` would be an out-of-vocabulary value for a consumer that keys on it. **Needs the maintainer's confirmation.** |
| `owner`, dates, `supersedes`/`superseded_by` | not defined | written as extra keys (allowed). `supersedes` is a list of bundle paths, `superseded_by` one path |
| "Human-captured entries use the `human:` actor prefix" | `human:<id>`; trust tiers key off `verified` by a human | `generated.by` and `verified.by` are `human:discord-<user id>` of the person who captured the entry. `verified.at` is the capture time. The user id is the stable Discord id; display names are only in `author`/`owner` |
| `sources` (`id`, `resource`, `title`, `author`) | same | `title` is `Message in #<channel>`; message text is never exported |

Not in the spec, so decided here: file names (`D-12-use-sqlite.md`, the slug is the title
lowercased to `[a-z0-9-]`, at most 48 characters, so it cannot contain a separator, a dot
or a drive letter), and the `human:discord-` id form.

## Untrusted text in the export

Chat text is untrusted data (plan section 13). The export is meant to be committed to a repository and
grepped by coding agents, so a title or name must not be able to change the structure of a
file or leave its directory. The escaping rules rest on two things known from the specs
(CommonMark allows backslash-escaping ASCII punctuation; YAML 1.2 double-quoted scalars
support `\"`, `\\`, `\n`, `\t` and `\uXXXX`); they were not re-read for this milestone, and
the tests check the output as text only. Choices:

- File names: ASCII slug only; the directory layout is fixed; every generated path is
  checked again before writing (one or two components, no leading dot, no separators).
- YAML values: always double-quoted, with `"`, `\`, control characters, line and paragraph
  separators, zero-width and bidirectional controls and the BOM escaped, so a value stays on
  one line.
- Markdown: whitespace collapsed to one line, invisible and bidirectional characters
  removed, `\ * _ [ ] < > # | ~ & !` and backticks escaped, and `://` broken up so text
  cannot become a clickable link. Each entry file and the index say the titles are data.
- Directories: refuse a non-empty directory unless `--force`; `--force` removes only files
  whose names match what the export writes, never follows a symbolic link, and creates new
  files with `create_new`.

## The `md` layout

The plan leaves it to M5. Decision: one file, `record.md`, with no frontmatter or footnotes:
`# Team record`, then `## Decisions`, `## Tasks`, `## Questions` (one `###` section per entry
with a bullet list of its facts), then `## History` (every audit event, oldest first). It
targets people who want to read, print or hand in the record. The OKF bundle remains the
format for agents and repositories. Recorded in ADR 0013.

## Dates typed by people

Plan section 8 asks for a small parser in `core` with no dependency. No library was
researched. Free-text dates are ambiguous in two well-known ways (day-first against
month-first, and "next Friday"), so the parser never guesses: numeric dates other than `YYYY-MM-DD` are rejected, a bare
weekday on that same weekday is rejected, and `next <weekday>` means that weekday in the
next Monday-to-Sunday week. The vocabulary and rules are in the `core::when` module docs.

## Not verified

- The OKF spec was read through a summarising fetch, and no OKF consumer or validator was
  run against the bundle (none was looked for beyond the spec page).
- Rendering in specific Markdown viewers was not checked; escaping is tested as text.

# M5 interactions: slash commands and context menus

Research date: 2026-11-10. Scope: plan section 7.3, the commands and context menus, how
they are registered, answered, deferred and limited.

## Discord's documentation

Pages read on 2026-11-10 through a page-summarising fetch tool (the `docs.discord.com`
copies the `discord.com/developers/docs` URLs now redirect to). Quotes below are what the
tool returned; re-check them against the pages before a release.

- [Receiving and responding](https://discord.com/developers/docs/interactions/receiving-and-responding):
  callback types `CHANNEL_MESSAGE_WITH_SOURCE` (4), `DEFERRED_CHANNEL_MESSAGE_WITH_SOURCE`
  (5, "ACK an interaction and edit a response later, the user sees a loading state") and
  `MODAL` (9). "Interaction tokens are valid for 15 minutes ... but you must send an initial
  response within 3 seconds of receiving the event. If the 3 second deadline is exceeded,
  the token will be invalidated." The original response is edited with
  `PATCH /webhooks/{application.id}/{interaction.token}/messages/@original`. Message data
  takes `content`, `embeds` ("up to 10"), `allowed_mentions` and `flags` (only
  `SUPPRESS_EMBEDS`, `EPHEMERAL`, `IS_COMPONENTS_V2`, `IS_VOICE_MESSAGE` and
  `SUPPRESS_NOTIFICATIONS` can be set). A modal has `custom_id` (1 to 100 characters),
  `title` ("max 45 characters") and 1 to 5 components. The interaction carries `member`
  ("guild member data for the invoking user, including permissions") in a server and
  `app_permissions`. For message commands `data.target_id` and `data.resolved.messages`
  hold the target.
- [Application commands](https://discord.com/developers/docs/interactions/application-commands):
  `PUT /applications/{application.id}/guilds/{guild.id}/commands` overwrites the guild's
  command list; "Guild commands update instantly". Slash command and option names match
  `^[-_\p{L}\p{N}...]{1,32}$` (lowercase); `USER` and `MESSAGE` command names "may be
  mixed case and can include spaces"; descriptions 1 to 100 characters; at most 25
  options; string options `max_length` up to 6000; 15 `MESSAGE` and 100 `CHAT_INPUT`
  commands per scope. Option types: `SUB_COMMAND` 1, `STRING` 3, `BOOLEAN` 5, `USER` 6,
  `CHANNEL` 7.
- [Component reference](https://docs.discord.com/developers/components/reference): "Action
  Row with Text Inputs in modals are now deprecated", and "The `label` field on a Text
  Input is deprecated in favor of `label` and `description` on the Label component". A
  submitted text input arrives as `{ "type": 4, "id": 2, "custom_id": ..., "value": ... }`.
- [Message resource](https://docs.discord.com/developers/resources/message): embed title
  256, description 4096, 25 fields, field name 256 and value 1024, footer 2048, author 256,
  and at most 6000 characters over all embeds of a message; content 2000; `EPHEMERAL` is
  `1 << 6`; an empty `parse` list in `allowed_mentions` suppresses all mentions.

Not found on these pages: a statement that answering an interaction needs no Send
Messages permission. That is spike S2, still open; `docs/guides/discord-bot.md` has the
manual check.

`twilight-model` 0.18 (already in the tree) has the `Label` component and the modal user
select, and `twilight-http` 0.18's interaction client has `create_response`,
`update_response` and `set_guild_commands`; `twilight-validate` counts embed lengths in
`char`s. No new crate was needed.

## What the implementation does with it

- **Registration:** guild commands, one bulk overwrite on the first `READY` (it carries
  the application id). Global registration is a config option in plan section 7.3, but
  section 12 names no field for it, so it is not built (open question).
- **Answering:** one callback per interaction. `/catchup` and `/search` always defer;
  everything else answers directly if it finishes within 1.8 s and defers otherwise.
  "Mark as task" answers with its modal, which cannot follow a deferral, so a slow store
  gets a "try again" note instead. Follow-up messages are new messages and are not used;
  the read-only guard denies them.
- **Modal:** two `Label` components, an optional user select for the owner (no guessing a
  person from a typed name) and an optional short text input for the due date. Its custom
  id carries the channel and message; on submit the message must still be stored and
  readable by the submitter.
- **Payloads** are read from the raw JSON, like messages in `crate::mapping`: the
  `twilight-model` `Interaction` type fails as a whole when a nested object lacks a field
  (for example a resolved message), and the bot must still be able to answer.
- **Text and limits:** chat text is put on one line, stripped of control, bidirectional
  and zero-width characters, backslash-escaped for markdown (so no masked links or mention
  markup), and `@` gets a zero-width space; `allowed_mentions` parses nothing. Lengths are
  counted in UTF-16 code units, never fewer than the characters Discord counts.
- **Who sees what:** commands are open to every member, but the bot reads channels some
  members cannot. Replies show chat-derived items only from channels the member can read,
  computed from the guild's roles and each channel's overwrites (the same calculation as
  `doctor`, from the same two read-only `GET`s, cached for 60 s); public replies only what
  `@everyone` can read. When the access data cannot be fetched, nothing chat-derived is
  shown. Plan section 7.3 does not ask for this; without it `/search` would show any
  member messages from channels they cannot open.
