# S3 spike: rmcp streamable HTTP behind bearer auth

Date: 2026-11-05. Question: does ADR 0006 (MCP over streamable HTTP with personal bearer
tokens) work with the official Rust SDK `rmcp`, mounted in axum? Code: `crates/teamctx-server`
(`src/lib.rs`, `src/auth.rs`, `src/mcp.rs`, `tests/mcp_http.rs`, `examples/s3_server.rs`).

Sources were read on 2026-11-05. Reddit cannot be scraped; one search pass for rmcp and
Claude Code auth threads returned only GitHub and docs.rs results, so social posts play no
part here. Search-engine summaries are marked "lead" and were checked against a primary
source where one was reachable.

## 1. Prior art

### Specification (primary)

- [Transports, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http).
  - One endpoint; every message is a POST; the reply is either one JSON object or a
    request-scoped SSE stream, and the client must accept both.
  - 2026-07-28 removed protocol-level sessions and the GET stream. A server that supports
    only this revision answers GET/DELETE with 405 and ignores `Mcp-Session-Id`.
  - Every POST carries `MCP-Protocol-Version`; the body repeats it in
    `_meta.io.modelcontextprotocol/protocolVersion`, and a mismatch is a 400.
  - Servers MUST validate `Origin` and answer 403 when it is present and invalid. They
    SHOULD bind to localhost when run locally and SHOULD authenticate every connection.
  - Servers SHOULD send `X-Accel-Buffering: no` on SSE responses (rmcp does).
- [Authorization, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).
  - Authorization is OPTIONAL. When an HTTP server supports it, it SHOULD follow the spec,
    which is OAuth 2.1 based: the server acts as a resource server, MUST implement RFC 9728
    protected resource metadata, and a 401 SHOULD carry
    `WWW-Authenticate: Bearer resource_metadata="...", scope="..."`.
  - Token transport is plain: `Authorization: Bearer <token>` on every request, never in
    the query string. Invalid or expired tokens MUST get 401; insufficient scope gets 403.
  - A static personal token is outside the OAuth flow. The spec does not forbid it; it
    does not describe it either. What we can honour from it: the header form, 401 for a
    bad token, no query-string tokens, and a `WWW-Authenticate: Bearer` challenge.
    `resource_metadata` is omitted on purpose, because there is no metadata document to
    point to until OAuth lands in v0.2.

### rmcp (primary: crate source and changelog of 3.8.0, released 2026-10-23)

- Streamable HTTP server is `StreamableHttpService`, a `tower_service::Service`, mounted
  with `Router::nest_service("/mcp", service)`. The crate's own tests use exactly that.
  Features needed: `server`, `macros`, `transport-streamable-http-server`.
- Protects against DNS rebinding by default: `allowed_hosts` defaults to
  `localhost`, `127.0.0.1`, `::1`; any other `Host` gets 403. A public deployment must set
  it, or every request behind a real hostname fails with a 403 that looks like an auth bug.
  `allowed_origins` is empty by default, which disables Origin checks; the
  `enforce_origin_validation()` builder turns them on with an empty list (any `Origin` is
  rejected).
- `legacy_session_mode` (default `true`) mints in-memory sessions for pre-2026-07-28
  clients. Requests that negotiate 2026-07-28 are always stateless.
- Changelog items relevant to this stack: 3.6.0 "answer a session-less non-initialize POST
  with 400" (#1377); "release the session map lock before waiting on a session" (#1323);
  3.7.0 "keep 401/403 status when the body is a JSON-RPC error" (#1341) and "allow
  cross-origin `resource_metadata` urls" (#1302). rmcp also has an `auth` feature (OAuth
  client side); not needed here.
- Issue lead (title and date from a GitHub issue search listing, not opened):
  [rust-sdk #559](https://github.com/modelcontextprotocol/rust-sdk/issues/559), "401
  session not found once MCP server is restarted on an existing client session", closed
  2026-03-11. It is the reason to avoid in-memory sessions (see 2.3).

### Other Rust servers behind auth (leads, from docs.rs source pages found by search)

Several rmcp-based crates (`rmcp-server-kit`, `rsigma-mcp`, `aingle_cortex`,
`winx-code-agent`) mount `StreamableHttpService` with `nest_service("/mcp", ...)` and put a
bearer check in an axum layer, answering 401 on a mismatch. Their allowed-host handling
starts from the loopback defaults and adds public hostnames. I did not audit them; the
shape matches ours, which is the only claim made.

### Claude Code as client (primary: two GitHub issues, read 2026-11-05)

- [claude-code #61376](https://github.com/anthropics/claude-code/issues/61376) (opened
  2026-05-22, closed 2026-05-27): an HTTP MCP server answered 401 with
  `WWW-Authenticate: Bearer error="invalid_token"` and no `resource_metadata`; Claude Code
  showed "Failed to connect" in `claude mcp list` instead of starting OAuth. The thread's
  workaround was a static `Authorization` header in the server config. The maintainer's
  fix concerns how a parse error in OAuth discovery is classified, not a well-known probe.
- [claude-code #29562](https://github.com/anthropics/claude-code/issues/29562) (opened
  2026-02-28, closed 2026-03-20): custom `-H` headers were not sent during session setup
  in the reporter's build, so a bearer-protected server saw 401. Follow-ups #28293 and
  #33817 track related header problems; the page does not say they are fixed.
- Reading: a static token in `headers` is the supported route for a non-OAuth server, but
  header handling has regressed before. T03b must test the installed Claude Code version,
  and the token must reach the server on the very first request (`initialize` or
  `server/discover`).

## 2. Result

`cargo test -p teamctx-server` runs the server on `127.0.0.1:0` and drives it with
`reqwest` over real HTTP. Eight integration tests (`tests/mcp_http.rs`) and three unit tests
(header parser, constant-time comparison, `Secret`) pass on Windows. Linux and macOS were
not run here; CI will cover them.
rmcp 3.8.0 compiles on Rust 1.89 (`cargo +1.89 check --workspace --all-targets --locked`).

### 2.1 What was proven

| Behaviour | Result |
|---|---|
| `/mcp` mounted with `nest_service` behind `middleware::from_fn_with_state` | works; middleware runs before rmcp |
| No header, `Bearer`, `Bearer `, `Basic ...`, wrong token, token plus extra word, token prefix, scheme-less token | all `401` with `WWW-Authenticate: Bearer realm="teamctx"` (missing) or `... error="invalid_token"` (rejected) |
| Token only in `?access_token=` | `401` |
| `bearer <token>` (lowercase scheme) | accepted (RFC 9110: scheme is case-insensitive) |
| `initialize` then `notifications/initialized` then `tools/list` with the token | `200`, `202`, `200`; the list holds one tool, `ping`, with `annotations.readOnlyHint: true` |
| `tools/call ping` | returns `pong from the Example Team record` |
| 2026-07-28 request with no `initialize` (`MCP-Protocol-Version`, `Mcp-Method` and `_meta`) | `200`; `tools/list` answers |
| Valid token with `Origin: https://evil.example` | `403` (rmcp, after auth) |
| Valid token with `Host: evil.example` | `403` (rmcp host allow-list) |
| `GET` and `DELETE` with a valid token | `405`, as the spec advises for a stateless server |
| Token comparison | constant time over the longer input; no new dependency |
| `Secret<String>` | `Debug` prints `Secret(***)`, `Display` prints `***` |

### 2.2 Session ids and response framing

- With `legacy_session_mode(false)` the server never sends `Mcp-Session-Id`, not even for a
  legacy `initialize` (protocol 2025-11-25). Later requests work with no session header, so
  the client needs no state and a server restart strands nobody. Tested for 2025-11-25 and
  2026-07-28.
- With rmcp's default (`legacy_session_mode(true)`) a legacy client gets an in-memory
  session. After a restart its id is unknown. That was not exercised here; the choice is
  made from the rmcp changelog and issue #559 above, so treat it as a lead for T12.
- Replies come back as `Content-Type: text/event-stream` with one `data:` event, even for
  a single request/response (`json_response` is off). A client must read SSE. Setting
  `with_json_response(true)` should return plain JSON when no notifications are sent;
  worth a test in T12 if a client turns out to dislike SSE. The test helper accepts both.
- Notifications get `202 Accepted` with no body.

### 2.3 Things T11 and T12 must carry forward

1. `allowed_hosts` is a deployment setting: behind `https://team.example` the list needs
   `team.example`. Put it in the config and in `doctor`.
2. Keep `enforce_origin_validation()`; agents send no `Origin`, browsers always do.
3. Apply the auth layer to the MCP sub-router only, so `/healthz` and the web routes can
   have their own rules (done here with `Router::merge`).
4. Replace the single static token with the T11 store: hash the presented token with
   SHA-256 and compare digests in constant time, update `last_used_at`, and rate limit
   failures (ADR 0006). The 401 body is empty by design.
5. Pass the `Authorization` header on the first request; nothing here reads the body
   before authenticating.
6. The workspace sets rmcp to `default-features = false` with `server`, `macros` and
   `transport-streamable-http-server`. That is enough for the tool macros and the HTTP
   transport. `server` already includes `schemars`, which T12's tools with parameters and
   `outputSchema` will need.
7. Dev-only `reqwest` with the `rustls` feature builds fine; `cargo deny check` passes
   with no licence change.

### 2.4 Not covered

- A real MCP client (Claude Code, Codex, Cursor) connecting. That is T03b.
- The session-restart behaviour under `legacy_session_mode(true)`.
- The rate limit on repeated failures (T11/T12).
- TLS: terminate it in a reverse proxy or tunnel (plan section 13).

### 2.5 Promotion

Clean enough to promote: `secret.rs` is a placeholder for T11's real `Secret` (rename or
move it then), `auth.rs` keeps its shape but swaps the token source, and `mcp.rs` holds the
only throwaway, `PingServer`. `lib.rs::router` and `tests/mcp_http.rs` (helpers and 401
cases) carry over.

## 3. Verdict: keep ADR 0006

Streamable HTTP at `/mcp` behind bearer-token middleware works with rmcp 3.8.0 in axum 0.8,
on the pinned MSRV, with no extra crates. No change to the ADR text is needed. Notes for
the ADR's follow-ups (not edited here; ADRs are outside this task's paths):

- The 401 challenge has no `resource_metadata`. Claude Code issue #61376 shows that a
  client may report "Failed to connect" rather than "needs authentication" for that shape;
  with a configured static header that is the right failure for a bad token.
- State that `Host` and `Origin` are validated in addition to the token.

## 4. Connecting Claude Code (for T03b)

Start the spike server with a throwaway token (nothing is printed):

```sh
TEAMCTX_S3_TOKEN=tctx_test_local_only cargo run -p teamctx-server --example s3_server
# listens on http://127.0.0.1:8787/mcp ; override with TEAMCTX_S3_ADDR
```

Register it, using the command the plan prints (section 10.1):

```sh
claude mcp add --transport http --scope user teamctx-s3 http://127.0.0.1:8787/mcp \
  -H "Authorization: Bearer tctx_test_local_only"
```

Equivalent project file `.mcp.json` (do not commit a real token; this one is a fake):

```json
{
  "mcpServers": {
    "teamctx-s3": {
      "type": "http",
      "url": "http://127.0.0.1:8787/mcp",
      "headers": { "Authorization": "Bearer tctx_test_local_only" }
    }
  }
}
```

Check: `claude mcp list` should show `teamctx-s3` connected; asking Claude to call `ping`
should return `pong from the Example Team record`. Also try a wrong token (expect a
failed connection, and a 401 in the server's access log if one is added) and quote the
header with double quotes; single quotes in some shells send the literal text. Remove it
afterwards with `claude mcp remove teamctx-s3`. Expected snags from the issues above:
older builds not sending `-H` headers during session setup.

For T03b, run the test with the installed Claude Code version and record it here.

### T03b result (2026-11-05)

Claude Code 2.1.308 on Windows connected to the running `s3_server` example:
`claude mcp list` reported `Connected` with the configured Authorization header.
Changing the throwaway token produced `Failed to connect` and an explicit HTTP 401.
Both registrations used a separate temporary `CLAUDE_CONFIG_DIR` and were removed
after the checks; the user's normal MCP configuration was untouched. Workspace
integration tests separately call `ping` and assert the exact fictional response.
A model-driven `ping` call was not attempted ; this checks client transport and auth compatibility only.
