# 0001. Rust

- Status: Accepted
- Date: 2026-11-04
- Deciders: maintainer
- Plan reference: §3 D1, §5, §16, §19

## Context

`teamctx` is one self-hosted program that a team runs on one always-on machine (plan
§4). In a single process it holds a Discord gateway connection, owns a SQLite writer,
serves an HTTP API and an MCP endpoint, and optionally calls an LLM provider (§5.2).

Releases must ship as ready-made binaries for Linux (x86_64 and aarch64, musl), macOS
(x86_64 and aarch64) and Windows (x86_64), with shell and PowerShell installers (§16).
The host is a team member, not an operator, so "download one file and run it" matters.
The domain logic in `core` has no I/O and no async (§5.1), which suits a type system
that makes illegal states hard to express.

The plan also records a risk: the Rust learning curve may slow delivery (§19). The
maintainer's Rust experience is an open question (§20, item 2).

## Decision

Write `teamctx` in Rust on the stable toolchain, with the MSRV pinned in
`rust-toolchain.toml`. Use a Cargo workspace laid out as in plan §5.4. Libraries return
typed errors with `thiserror`; `anyhow` appears only in the binary crate (§17).

The decision is checked in milestone M1. The spikes S1 to S4 are the first real Rust
code on the critical path (gateway, interaction replies, MCP over HTTP, bundled FTS5).
Go is the documented fallback, and the keep-or-switch call is made by the end of M1
(§19). The go/no-go threshold is not defined in the plan (§20, item 2).

## Alternatives considered

- **Go.** The fallback. Likely a gentler learning curve for the maintainer and easy
  static binaries. Not evaluated beyond that: the choice of Discord and MCP libraries
  in Go has not been researched, and the M1 spikes are what would test it.
- **TypeScript on Node.** Shipping a single native binary would mean bundling a
  runtime or asking hosts to install one, which works against the install story in
  US-1 (under 10 minutes).
- **Python.** Same distribution problem as Node, and no advantage for a long-running
  concurrent service with a strict single-writer database.

## Consequences

### Good

- One self-contained binary per platform, built and attested by `cargo-dist` (§16).
- The crate boundaries in §5.1 are enforced by the compiler: `core` cannot do I/O.
- The libraries the plan relies on (`twilight`, `rmcp`, `axum`, `rusqlite`) are Rust
  crates, so there is no foreign-function layer to maintain.

### Bad

- Slower start-up and slower iteration if the learning curve bites (§19).
- Fewer contributors may be comfortable with Rust than with Go or TypeScript.
- Compile times and cross-OS CI cost are higher.

### Follow-ups

- M1: write down the result of the spikes and the keep-or-switch decision. If the
  decision changes, supersede this ADR and the ones that depend on it.
- M0: pin the toolchain and MSRV; CI builds the MSRV (§16).
