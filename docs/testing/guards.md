# Security guards

Two promises in plan section 13 and [ADR 0005](../adr/0005-read-only-boundary.md) are
checked by `cargo test` on every CI run: the bot never writes to Discord except to answer
interactions, and no secret reaches a log. All values in these tests are fake.

## Read-only guard

`crates/teamctx-discord/tests/readonly.rs` lexes every product source file
(`crates/*/src`, `examples`, `benches`, `build.rs` and `xtask/src`). Comments are dropped
and string literals are kept apart from code, so a name in a doc comment or a log message
is not a hit. It fails on:

| Rule | Catches |
|---|---|
| R1 | A call or path to a `twilight-http` write method: messages, reactions, pins, threads, channels, roles, members, bans, prunes, automod, webhooks, invites, guild settings, follow-ups. |
| R2 | Any mention of a write request builder or `Route` variant (`CreateMessage`, `Route::CreateReaction`, ...). |
| R3 | In a file that names `twilight_http`, any write-shaped method or type (`create_*`, `update_*`, `delete_*`, `add_*`, `remove_*`, `set_*`, ...) that is not on the allow-list. This catches methods twilight adds later. |
| R4 | `POST`, `PUT`, `PATCH` or `DELETE` (constants, `.post(` style calls or method strings) in a file that holds a Discord REST route in a string literal, unless every Discord route in that file is an interaction route. |

**Allow-list** (plan section 7.3, nothing else): `create_response` and
`POST /interactions/{id}/{token}/callback` to answer; `update_response` and
`PATCH /webhooks/{app}/{token}/messages/@original` to edit a deferred answer;
`set_guild_commands`, `set_global_commands` and `PUT .../commands` to register the slash
commands on start. Follow-up messages and deleting the response are denied. Widening the
list changes ADR 0005 and needs the maintainer's approval; a test pins it.

The guard is itself tested: deliberately bad snippets (twilight calls, aliases, raw
identifiers, builders, raw `reqwest` writes, method strings) must be flagged, and
interaction replies, reads, jump links and the store's local `delete_message` must pass.

**Not covered.** Routes split across several string literals, HTTP methods or URLs passed
in from another file, and code generated by other crates' macros. Integration tests are
not scanned (they never ship; the sync fakes model Discord-side deletes). Keep Discord
HTTP in one thin adapter so R3 and R4 see the whole call.

## Secrets guard

Fake values: a bot token, an LLM key containing `+`, `/` and `=` (so percent-encoding
changes it) and a well-formed `tctx_` access token. Each check searches the raw value,
hex in both cases, percent-encoding in both cases, and standard and URL-safe base64 at
all three byte alignments (so a value inside a longer encoded string, such as a Basic
auth header, is still found). Failures name the secret and the place, never the text.
Each log-capture test installs a `tracing_subscriber::fmt` subscriber at TRACE and first
asserts that its own canary event was captured, so an unwired capture cannot pass.

| Path | Test | What runs |
|---|---|---|
| auth, tokens | `crates/teamctx-server/tests/secrets.rs` | A token stored by hash, accepted, revoked (then 401), the bot token and LLM key presented as bearer, Basic and malformed headers, until lockout (429); `Debug` of token and auth types. `Secret<T>` prints `***` in every format, inside structs, options, results, errors and `tracing` fields. |
| `/ask` | `crates/teamctx-llm/tests/secrets.rs` | The pipeline on the demo record against a local mock provider, both adapters: success, 401 and 500 bodies that echo the key, a malformed body, a redirect carrying the key, a timeout and a refused connection; base URLs with the key in them; `ApiKey` errors. |
| config, token CLI | `crates/teamctx/tests/guards_secrets.rs` | The binary with the secrets in its environment and `RUST_LOG=trace`: `doctor`, `init`, and secrets pasted into config fields, options and override variables. `token create` prints a token once; `list`, `revoke`, duplicates and a token pasted as a name never print it. |
| sync | `crates/teamctx/tests/guards_secrets.rs` | `sync_guild` against a fake Discord whose messages, names, topics, authors and attachments carry the secrets, plus garbled, forbidden, rate-limited, 401, 5xx and transport failures. |

**Known defects** (ignored tests, to be fixed by the crate owners):

- `a_key_pasted_as_the_variable_name_is_not_echoed` (`teamctx-llm`): a key made of
  letters, digits and `_` is a valid variable name, so `llm.api_key_env` accepts it, and
  the "not set" error prints it.
- `malformed_payload_values_are_not_quoted_in_errors` (`teamctx`): `MapError` keeps
  serde's message, which quotes the offending value, so a malformed Discord payload puts
  its text into `SyncError`'s source chain.

**Not covered.** The live gateway and twilight adapters do not exist yet; when they land,
their errors must not carry headers or the token, and these tests must run them.
`teamctx init` echoes free-form config values back as a template, so a secret pasted into
`model`, `base_url` or `timezone` is printed to the operator's own terminal. Memory is
not zeroed (plan section 17 has no `zeroize`). Usage errors echo a stray command-line
argument, as most CLIs do.
